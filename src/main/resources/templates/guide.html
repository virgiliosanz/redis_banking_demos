UC1: Authentication Token Store

What to say

"When a user authenticates, we need to store their token somewhere fast and reliable. Redis is perfect for this — we store the token as a Hash with a TTL, so it auto-expires when the session ends. Any microservice in your architecture can validate the user by checking Redis."

Demo steps

  1. Click "Login" with the demo credentials
  2. Show the generated token and its TTL countdown
  3. Click "Validate Token" — show it returns valid
  4. Wait or click "Logout" — show the token is gone
  5. Try to validate again — show it fails

Key Redis commands

  • HSET uc1:token:{id} ... — store token
  • EXPIRE — auto-cleanup
  • HGETALL + TTL — validate token and inspect remaining lifetime

Why these data structures?

  • Hash: A token has multiple fields (userId, role, issuedAt, device). Hash stores them as a single unit — one key, multiple fields. Alternative would be a JSON string, but Hash lets you read/write individual fields without deserializing.
  • TTL (EXPIRE): Tokens must expire. Instead of running a cleanup job ("delete all tokens older than X"), Redis auto-deletes the key when the TTL hits zero. Zero maintenance, zero memory leaks.

Under the hood

  • AuthTokenController routes /api/auth/login, /validate, /logout, and /token/{token} into AuthTokenService.
  • login() generates a UUID token and stores a Redis Hash at uc1:token:{tokenId} with putAll + expire.
  • validateToken() reads the full Hash plus TTL so the UI can show both token fields and the live countdown.
  • logout() simply deletes the token key, which makes the invalidation step immediate and easy to demo.

Talking points

  • Sub-millisecond token validation vs database lookup
  • Distributed: any service can check the token
  • TTL = automatic session expiry, no cleanup jobs needed

UC2: Session Storage

What to say

"Once authenticated, we need to store session state — form data, user preferences, recent actions. Instead of keeping this in the app server (which doesn't scale) or hitting the database on every request, we use Redis as a distributed session store."

Demo steps

  1. Create a new session — show the Redis Hash and paired auth token
  2. Open the session info view — show all stored fields for that username
  3. Check the TTL endpoint — explain session expiry countdown
  4. Validate the token — show Redis resolves it back to the username
  5. Logout — both the session Hash and token String disappear

Key Redis commands

  • HSET / HGETALL — session CRUD
  • EXPIRE — auto-cleanup on inactivity
  • SET uc2:token:{id} — token → username lookup

Why these data structures?

  • Hash: A session is a collection of key-value pairs (userName, lastPage, cart, preferences). Hash maps directly to this shape. HSET/HGET let you update individual fields without reading the whole session — important when sessions are large.
  • TTL: Abandoned sessions auto-expire. No background cleanup process needed, and the demo can show the same TTL on both the session Hash and the token lookup key.

Under the hood

  • SessionController exposes /api/session/login, /info/{username}, /ttl/{username}, /logout, and /validate.
  • SessionService.login() writes a Hash at uc2:user:{username} and a String at uc2:token:{uuid} with the same 5-minute TTL.
  • The validation path is token → username via Redis String; the info/TTL paths read the session Hash and expiry directly.
  • logout() first reads the token field from the Hash, then deletes both Redis keys so the cleanup is easy to explain live.

Talking points

  • Stateless app servers: any instance can serve any user
  • Redis vs sticky sessions: horizontal scaling
  • TTL handles abandoned sessions automatically

UC3: User Profile Storage

What to say

"In banking, a user profile is scattered across multiple systems — accounts, activity logs, preferences. Redis aggregates all of this into a single fast-access profile. When the user logs in, one call to Redis gives you everything."

Demo steps

  1. Select a user (e.g., "María García")
  2. Click "Load Profile" — show data aggregated from Accounts DB, Activity DB, Preferences DB
  3. Modify a field (e.g., notification preference)
  4. Click "Sync Back" — changes written to source databases

Key Redis commands

  • HSET with multiple fields — aggregated profile
  • HGETALL — single read for complete profile
  • HSET field value — partial profile updates

Why these data structures?

  • Hash: A user profile is naturally a flat map of fields (name, email, accountType, lastLogin, preferences). Hash is the perfect fit — HGETALL returns the complete profile in one call, HSET updates specific fields without touching the rest.
  • Prefixed fields: The service flattens three source systems into one Hash using prefixes like account_, activity_, and pref_, which keeps the merged profile readable in Redis.

Under the hood

  • UserProfileController drives load, read, update, sync, and list actions through UserProfileService.
  • loadProfile() merges three in-memory source maps and writes one Hash at uc3:user:{userId} with a 10-minute TTL.
  • getProfile() uses HGETALL-style reads, while updateProfile() applies field-level HSET updates without rewriting the whole object.
  • syncProfile() is intentionally simulated: it confirms the write-back step for the presenter without mutating the mock source datasets.

Talking points

  • Redis collapses three lookups into one fast profile read during the active session
  • Field-level updates keep profile writes simple and explicit
  • The demo shows the write-back pattern without hiding the source-system boundaries

UC4: Rate Limiting

What to say

"With PSD2 and Open Banking, your APIs are exposed to third parties. You need to protect them. Redis makes rate limiting trivial — INCR a counter, check the limit, set a TTL. It's atomic and fast."

Demo steps

  1. Click "Send Request" a few times — see counter increment
  2. Hit the limit — see the request denied in red
  3. Wait for the window to reset — see it allow again
  4. Open the status view — show remaining budget and retry-after from Redis TTL

Key Redis commands

  • INCR — atomic counter
  • EXPIRE — window reset
  • GET + TTL — inspect current usage without consuming another request

Why these data structures?

  • String + INCR: This implementation is intentionally the simplest useful limiter: one String counter per client, atomically incremented on every call.
  • TTL (EXPIRE): The first hit in a new window sets the expiry, so Redis automatically resets the budget without any cleanup job.

Under the hood

  • RateLimitController calls checkRateLimit(), getStatus(), and reset() in RateLimitService.
  • Each client uses one Redis String key: uc4:{clientId}.
  • checkRateLimit() does INCR, sets EXPIRE only when the counter is first created, then returns remaining budget and retry-after based on TTL.
  • This demo is fixed-window only — no Sorted Set or token bucket logic is hiding behind the UI.

Talking points

  • Atomic operations = no race conditions under load
  • Fixed window is often enough when you want the simplest operational story
  • Per-user, per-API-key, per-IP — flexible key design

UC5: Transaction Deduplication

What to say

"Duplicate payments are a real problem in banking — network retries, user double-clicks, system failures. Redis gives you instant dedup with one atomic command: SET NX with a TTL. If the transaction fingerprint already exists, the retry is rejected immediately."

Demo steps

  1. Submit a transaction — see it accepted
  2. Submit the same transaction again — see it rejected as duplicate
  3. Submit a different transaction — accepted
  4. Show the 5-minute dedup window and the generated transaction fingerprint

Key Redis commands

  • SET key value NX EX ttl — atomic check-and-set
  • DEL / key expiry — clear markers when the dedup window ends

Why these data structures?

  • String with SET NX EX: The transaction fingerprint becomes the key. NX (Not eXists) ensures the write only succeeds once, and EX keeps the dedup window bounded automatically.
  • Deterministic fingerprint: The service hashes sender, receiver, amount, and a 5-minute time window, so retries land on the same Redis key while genuinely new transfers do not.

Under the hood

  • DeduplicationController sends POST /api/dedup/submit into DeduplicationService.submitTransaction().
  • The service builds a short SHA-256 fingerprint and uses key uc5:{txHash} in Redis.
  • Acceptance vs duplicate is decided by a single setIfAbsent(..., TTL) call, which maps directly to SET NX EX.
  • The visible transaction log is a bounded in-memory list for the UI; Redis only stores the dedup marker for the active time window.

Talking points

  • SETNX-style dedup is atomic — impossible to have two retries slip through simultaneously
  • The TTL defines the business dedup window explicitly
  • This demo keeps the pattern simple and deterministic instead of adding probabilistic filters

UC6: Fraud Detection (Transaction Risk Scoring)

What to say

"This demo focuses on three fast fraud signals: transaction velocity, amount thresholds, and geo anomalies. Redis keeps the rolling transaction window in a Sorted Set and appends every scored transaction to a Stream so the dashboard can show both the live decision and the audit trail."

Demo steps

  1. Submit a normal transaction — see LOW risk score (green)
  2. Submit a high-amount transaction — see MEDIUM risk
  3. Submit rapid-fire transactions (burst) — velocity check triggers HIGH risk
  4. Submit from unusual location — see CRITICAL risk
  5. Show the transaction stream log

Key Redis commands

  • ZADD + ZRANGEBYSCORE — velocity tracking
  • XADD / XRANGE — transaction stream
  • ZREMRANGEBYSCORE — evict transactions outside the rolling window

Why these data structures?

  • Sorted Set (velocity tracking): ZADD stores each transaction scored by timestamp. ZRANGEBYSCORE with a time window (last 5 minutes) instantly counts recent transactions. This is how velocity checks work — "how many transactions in the last X minutes?"
  • Stream (audit trail): XADD appends each scored transaction with amount, country, risk score, and factors, so the dashboard can replay the recent fraud decisions in order.
  • Java scoring on top of Redis state: Redis holds the rolling evidence, while the risk score itself is calculated in service code from amount, velocity, and geo rules.

Under the hood

  • FraudController posts each evaluation request to FraudService.evaluateTransaction() and exposes the recent Stream view separately.
  • Velocity data lives in Sorted Sets uc6:velocity:{cardNumber}; startup seeds baseline entries so the rolling-window demo is never empty.
  • The service adds the new transaction with ZADD, counts the last 5 minutes with ZRANGEBYSCORE, removes stale entries, and computes the risk score in Java.
  • Every evaluated transaction is appended to uc6:stream:transactions, which powers the audit panel via reverse-range reads.

Talking points

  • Sorted Sets for time-windowed velocity checks
  • Streams give you a replayable fraud decision log without a separate queue
  • The risk score is explainable because each rule is visible in the response payload

UC7: Feature Store

What to say

"This use case shows Redis as an online feature store for banking decisions. Each client has pre-seeded feature vectors in Redis Hashes, the service fetches them in one read for mock inference, and live transactions update the real-time features immediately."

Demo steps

  1. Show pre-loaded client features (3 different risk profiles)
  2. Select a client — view both feature-set versions stored in Redis
  3. Run inference — compare Redis fetch time with the simulated database latency
  4. Simulate a transaction — watch the real-time counters and risk score update
  5. Re-run inference — see the decision reflect the updated features

Key Redis commands

  • HSET / HGETALL — feature storage
  • HINCRBY — real-time feature updates
  • HSET — recompute derived values such as averages and risk score

Why these data structures?

  • Hash: ML features are naturally key-value pairs (feature_name → value). Hash stores the complete feature vector for a client. HGETALL serves the model in <1ms. HINCRBY updates counters (tx_count, login_count) without read-modify-write.
  • Versioned keys: The demo keeps feature_set_v1 and feature_set_v2 side by side so the presenter can explain legacy vs richer real-time features without changing the UI flow.

Under the hood

  • FeatureStoreController exposes client listing, feature reads, inference, and transaction simulation through FeatureStoreService.
  • The service seeds two Redis Hashes per client: uc7:feature_set_v1:client:{id} and uc7:feature_set_v2:client:{id}.
  • runInference() fetches the full Hash, scores it in Java, and returns a side-by-side comparison against a simulated 150ms database fetch.
  • simulateTransaction() updates counters and derived features with HINCRBY/HSET, then recomputes the mock risk score for the live demo.

Talking points

  • Online feature store for ML model serving
  • Real-time feature updates (not batch)
  • Versioned feature sets let you compare model inputs without changing the serving path

UC8: Document Database

What to say

"Redis 8 includes a full document database with JSON support and a powerful query engine. You can store regulation documents, search them with full-text queries, and even do vector similarity search — all from Redis, with sub-10ms response times."

Demo steps

  1. Type a full-text search query (e.g., "customer authentication")
  2. Show results with relevance scores
  3. Switch to vector search mode — find semantically similar documents
  4. Try hybrid search — combine text filter + vector similarity

Key Redis commands

  • JSON.SET — store documents
  • FT.CREATE — index with TEXT + VECTOR fields
  • FT.SEARCH — full-text query
  • FT.SEARCH ... KNN — vector similarity

Why these data structures?

  • JSON (JSON.SET): Regulation documents have nested structure (title, sections, metadata, tags). JSON preserves this hierarchy natively. You can query nested fields with JSONPath.
  • RQE with TEXT fields: FT.CREATE indexes specific JSON fields for full-text search. The query engine handles stemming, stop words, and relevance scoring — like Elasticsearch, but inside Redis.
  • RQE with VECTOR fields: Same index can include vector embeddings. KNN search finds semantically similar documents even when the exact words differ. One index, two search modes (text + vector), combined in a single query.

Under the hood

  • DocumentSearchController routes search, list, query-by-field, read-by-id, and create requests into DocumentSearchService.
  • Documents live as JSON records under uc8:doc:{id} and are indexed by idx:uc8:documents.
  • fullTextSearch(), vectorSearch(), and hybridSearch() each build the exact FT.SEARCH command string returned to the UI.
  • Embeddings are generated locally using BGE-small-en-v1.5 (384 dims, ONNX). No API key is needed for vector search.

Talking points

  • No need for Elasticsearch + separate vector DB
  • One database for text search + vector search + structured queries
  • Redis Query Engine supports full-text, numeric, tag, and vector fields
  • <10ms for document retrieval

UC9: AI Agent Memory + RAG

What to say

"AI agents need memory — both short-term (current conversation) and long-term (past interactions). Redis provides both, plus RAG retrieval for knowledge base search. This is the architecture behind every serious AI banking assistant."

Demo steps

  1. Start a conversation — ask about wire transfers
  2. Show the Memory Inspection panel — see the conversation Hash with TTL and stored messages
  3. Ask a follow-up — agent recalls context from short-term memory
  4. Ask about a topic from past interactions — agent retrieves from long-term memory (vector search)
  5. Ask a regulatory question — agent pulls from knowledge base (RAG)
  6. Show which memories and KB docs were retrieved

Key Redis commands

  • HSET + EXPIRE — short-term conversation memory
  • HSET + vector field + FT.SEARCH KNN — long-term memory and KB retrieval
  • FT.SEARCH KNN — regulation-doc retrieval and semantic cache lookup

Why these data structures?

  • Hash + TTL (short-term memory): The conversation lives in one Redis Hash keyed by session, with metadata fields plus a serialized messages array. TTL auto-expires inactive chats.
  • Vector indexes (long-term memory + RAG): Past interactions, KB articles, and semantic cache entries are Hash records with vector fields, so FT.SEARCH KNN can retrieve relevant context by similarity.
  • Semantic cache (Vector + TTL): Identical or similar questions hit a vector cache before calling the LLM. Saves tokens, reduces latency, cuts costs. TTL ensures the cache stays fresh.

Under the hood

  • AssistantController exposes synchronous chat, SSE streaming, conversation inspection, KB browsing, and semantic-cache stats through AssistantService.
  • Short-term state is stored at uc9:conversation:{sessionId}; AssistantService then fans out to MemoryService, KnowledgeBaseService, and SemanticCacheService.
  • MemoryService seeds uc9:memory:* / idx:uc9:memory, while KnowledgeBaseService owns uc9:kb:* / idx:uc9:kb and also queries UC8's regulation index.
  • Embeddings are generated locally by LocalEmbeddingService using BGE-small-en-v1.5; OpenAI is only used for chat completions when configured.

Talking points

  • Short-term memory: one session Hash with TTL = automatic cleanup
  • Long-term memory: vector search over past interactions
  • RAG: same Redis instance serves as vector store
  • No external vector database needed — Redis does it all

UC10: Cache-Aside Pattern

What to say

"This is what most people think of when they hear Redis — caching. But the cache-aside pattern is more than just GET/SET. You check Redis first, on a miss you fetch from the database and store the result with a TTL. Second request? Sub-millisecond. The key is the TTL — it controls freshness and auto-cleanup."

Demo steps

  1. Select a banking product (e.g., "Fixed Rate Mortgage")
  2. Click "Fetch Product" — first call is a CACHE MISS (~200ms)
  3. Click "Fetch Product" again — now it's a CACHE HIT (<1ms)
  4. Show the latency difference in the stats panel
  5. Click "Clear Cache" — evict the product
  6. Fetch again — back to MISS, then HIT on second fetch
  7. Show the hit ratio climbing as you make more requests

Key Redis commands

  • GET uc10:product:{id} — check cache
  • SET uc10:product:{id} ... EX 300 — store with TTL
  • DEL — cache eviction on data change

Why these data structures?

  • String (GET/SET): The simplest Redis data structure — one key, one value. For caching serialized objects, String is all you need. GET is O(1), SET EX combines write + TTL in one command.
  • TTL (EX): Controls cache freshness. A 5-minute TTL means data is never more than 5 minutes stale. When the TTL expires, the next request triggers a fresh database fetch. No invalidation logic needed for time-based freshness.
  • DEL: For write-through invalidation — when the source data changes, DEL the cached key. Next read triggers a fresh fetch. Simple, reliable, consistent.

Under the hood

  • CacheAsideController delegates fetch, single-key eviction, full eviction, and stats endpoints to CacheAsideService.
  • Products come from an in-memory mock database, while cache entries are JSON strings at uc10:product:{productId} with a 300-second TTL.
  • getProduct() is explicit cache-aside: GET Redis first, sleep 200ms to simulate the database on miss, then SET the cache.
  • Hit/miss counters stay in Java AtomicLongs so the presenter can explain latency savings without hiding the Redis calls.

Talking points

  • 200x speedup: 200ms → <1ms on cache hit
  • TTL = automatic freshness control, no stale data forever
  • Cache eviction on write for data consistency
  • This demo keeps the cache-aside logic explicit instead of hiding it behind annotations
  • Hit ratio is the key metric — aim for >80% in production

UC11: Real-time Transaction Monitoring

What to say

"Banks need to monitor transactions in real time — TPS, amounts, risk scores. Redis Streams are perfect for this. XADD ingests transaction events with auto-generated timestamp IDs, XRANGE queries them by time window, and the app aggregates into time buckets. You get a live dashboard with sub-millisecond writes and reads — using a core Redis data structure."

Demo steps

  1. Click "Start Simulation" — watch the chart build up (~2 TPS)
  2. Point out the metrics cards: TPS, total count, average amount
  3. Click "Inject Anomaly" — see the spike in the chart and the High Risk % jump
  4. Click "Stop" to pause, then "Reset" to clear
  5. Show the Redis CLI tab — explain XADD, XRANGE, XLEN

Key Redis commands

  • XADD — add a transaction event with amount and risk score fields
  • XRANGE — query entries in a timestamp range
  • XLEN — get total stream length
  • XTRIM — bound the stream with MAXLEN

Why these data structures?

  • Stream (XADD/XRANGE): Streams are an append-only log with auto-generated timestamp IDs. XADD writes a transaction event with all its fields (amount, type, risk). XRANGE reads entries in a time window. This is exactly what event sourcing needs — ordered, timestamped, queryable.
  • XLEN: Returns the stream length in O(1) — useful for total transaction count without scanning.
  • XTRIM MAXLEN: Bounds the stream to prevent unbounded growth. Keep the last 10,000 entries, older ones auto-deleted. Memory-safe by design.

Under the hood

  • TransactionMonitorController starts/stops the simulator, injects anomalies, and reads metrics/history from TransactionMonitorService.
  • Each generated transaction is XADDed to uc11:stream:transactions, and the stream is trimmed to 10,000 entries.
  • The simulator runs on a single scheduled executor at 500ms intervals, while injectAnomaly() adds a burst of high-risk events in one shot.
  • History queries read a Redis time range first and then aggregate TPS, averages, and risk buckets in Java for the chart.

Talking points

  • Redis Streams: append-only log with ms-precision timestamp IDs
  • XTRIM MAXLEN keeps the stream bounded (last 10,000 entries)
  • Aggregation done in Java: COUNT, AVG, SUM per 1-second bucket
  • Stream IDs are time-based — natural fit for time-range queries
  • Perfect for real-time dashboards, alerting, and anomaly detection

UC12: ATM & Branch Finder (Geospatial)

What to say

"Location matters in banking. Customers need to find the nearest ATM or branch, filtered by services. Redis Geospatial gives you sub-millisecond radius search. Combine it with JSON + Query Engine for rich filtering — geo plus type, services, hours — all in one query."

Demo steps

  1. Start with Native Geospatial tab — click Puerta del Sol preset
  2. Search with 2km radius — show ATMs and branches on the map
  3. Point out the GEOSEARCH command — simple, fast, returns distance
  4. Switch to JSON + Query Engine tab — same location
  5. Filter by type: ATM only — show how the FT.SEARCH query adds @type:{atm}
  6. Filter by service: advisor — only branches with advisor service
  7. Compare: native is simpler, RQE adds rich filtering in a single query

Key Redis commands

  • GEOADD — add coordinates to a sorted set
  • GEOSEARCH — radius search with distance, sorted
  • JSON.SET — store rich documents with location field
  • FT.CREATE with GEO + TAG fields — index for geo+filter queries
  • FT.SEARCH with @location:[lng lat radius km] — geo filter in RQE

Why these data structures?

  • Geo (GEOADD/GEOSEARCH): Redis Geo stores coordinates in a Sorted Set using geohash encoding. GEOSEARCH returns all points within a radius, sorted by distance — sub-millisecond for thousands of locations. No external geo database needed.
  • JSON + RQE (FT.SEARCH with GEO field): When you need geo + filtering (e.g., "ATMs within 2km that have deposit service"), JSON stores rich location documents and RQE combines geo radius with TAG/TEXT filters in a single query. More powerful than native geo, same Redis instance.

Under the hood

  • GeoFinderController exposes a native Redis geo path and a Redis Query Engine path through GeoFinderService.
  • Each location is loaded twice: GEOADD into uc12:geo:atms plus Hash metadata uc12:meta:{id}, and JSON.SET into uc12:branch:{id} indexed by idx:uc12:branches.
  • searchNative() runs GEOSEARCH and enriches each hit from the metadata Hash.
  • searchRQE() builds one FT.SEARCH query with geo radius plus optional @type and @services filters, then sorts the distances in Java.

Talking points

  • Native geo: O(N+log(M)) — extremely fast for pure proximity
  • RQE geo: combines geo with any other filter in a single query — no application-side filtering
  • Both approaches use the same Redis instance — no external geo database needed
  • Real-world: branch locators, delivery radius, fraud geo-fencing

UC13: Distributed Locking

What to say

"Wire transfers need mutual exclusion — you can't have two processes debiting the same account at once. Redis gives you distributed locking with a single command: SET key value NX EX. NX means 'only set if the key doesn't exist' — that's your lock. EX gives it a TTL — that's your deadlock prevention. And a Lua script ensures only the lock owner can release it."

Demo steps

  1. Select two accounts for a wire transfer
  2. Click "Transfer" — watch both accounts get locked (SET NX EX)
  3. Try a concurrent transfer on the same account — see it denied (lock held)
  4. Watch the lock auto-expire via TTL countdown
  5. Click "Release Lock" — see the Lua script verify ownership before deleting
  6. Show what happens when a lock holder crashes — TTL releases automatically

Key Redis commands

  • SET uc13:lock:{accountId} {clientId} NX EX 30 — atomic lock acquire
  • EVAL with Lua script — safe release (check owner, then DEL)
  • TTL — inspect remaining lock time
  • GET — check current lock holder

Why these data structures?

  • String with NX: The NX flag makes SET atomic — only one client can set the key. This IS the lock. No race conditions, no two-phase locking needed.
  • EX (TTL): Prevents deadlocks. If the lock holder crashes, the key expires automatically. No manual cleanup, no orphaned locks.
  • Lua scripting (EVAL): The release must be atomic — check owner AND delete in one step. Without Lua, another client could acquire between your GET and DEL. Lua runs server-side as a single atomic operation.

Under the hood

  • DistributedLockController routes acquire, release, info, and contention simulation requests into DistributedLockService.
  • Each lock is a Redis String at uc13:lock:{resourceId} written with SET NX EX semantics via setIfAbsent.
  • releaseLock() executes a Lua script that verifies the client id before deleting the key, so release stays atomic.
  • simulateContention() uses a small Java executor to show one winner and multiple blocked contenders against the same Redis lock.

Talking points

  • SET NX EX is the foundation of the Redlock algorithm
  • Lua scripts run atomically on the server — no interleaving
  • TTL = automatic deadlock prevention, even if the holder crashes
  • In production: consider Redlock for multi-instance Redis setups

UC14: Agent Memory Server

What to say

"UC14 is deliberately not a RAG demo. The agent only knows what we place into Redis AMS working memory and long-term memory. On every turn, the app calls AMS over REST — or MCP in tool-native agent setups — and AMS assembles the context from the active session plus semantically relevant memories. That gives you synchronous chat with memory, without having to bolt in a separate documents pipeline."

Demo steps

  1. Open the AMS status card and point out the base URL, MCP URL, namespace, and seeded-memory count
  2. Click "Seed demo memories" — show the curated banking long-term memories being posted to AMS
  3. Send a first question such as "Which payment rail should I use for a €500 transfer inside the EEA?"
  4. Open the Context Assembly panel — show working memory, KNN-retrieved long-term memories, and the final assembled messages
  5. Ask a follow-up question — show the session-specific working memory growing turn by turn
  6. Open the AMS traces panel — connect each REST call to the memory lifecycle without scraping Redis directly

Key Redis commands

  • PUT /v1/working-memory/{sessionId} — append or overwrite the session's active working memory held in Redis
  • POST /v1/long-term-memory/ — create durable semantic memory records for later recall
  • POST /v1/memory/prompt — assemble the final prompt from working memory plus retrieved long-term memory
  • FT.SEARCH ... KNN — underlying semantic lookup over the long-term memory index during context assembly
  • EXPIRE / session-scoped retention — keeps active conversation state bounded while long-term memory stays durable

Why these data structures?

  • Session-scoped working memory: The current conversation must be updated and fetched on every turn, so Redis gives AMS a very fast operational store for the active chat window.
  • Long-term semantic memory: Durable memory records need similarity retrieval, not exact-key lookups, so AMS uses Redis Query Engine vector search to recall relevant facts.
  • Separated short-term + long-term memory: The demo can clearly show what was just said versus what the agent remembered from prior seeded knowledge.
  • REST/MCP over the same Redis backend: Web apps can keep a simple synchronous REST flow, while agent frameworks can use MCP without changing the memory substrate.

Under the hood

  • AmsController is a thin REST facade over AmsDemoService, intentionally separate from UC9 so both memory patterns can be demoed side by side.
  • AmsDemoService talks to the external AMS via AmsClient: seed/reset memories, fetch working memory, call /v1/memory/prompt, and return traces.
  • Each chat turn follows the same flow: load working memory, append the user message, ask AMS to assemble context, call OpenAiService.chatCompletion(), then write the assistant reply back.
  • The Redis key patterns are owned by AMS itself, so this app deliberately surfaces the AMS REST/MCP contract rather than writing Redis keys directly.

Talking points

  • AMS gives agentic architectures a dedicated memory layer instead of forcing every team to hand-roll chat memory and context assembly
  • Memory-only flows are different from RAG: here the model answers from working memory + long-term memories, not from a documents corpus
  • The same AMS backend can serve browser apps via REST and tool-native agents via MCP
  • Synchronous chat is easier to demo live because every turn returns the full assembled context and final response in one payload

UC15: AI Guardrails for Banking Chat

What to say

"Before an AI answer reaches a banking customer, you need guardrails. Redis lets us enforce them in real time: rate-limit abusive users, route the question to the right policy bucket, detect and scrub PII, block prompt injection attempts, and keep an auditable event trail — all with sub-millisecond primitives."

Demo steps

  4. Repeat requests quickly — show the Redis-backed rate limiter step in
  5. Open the audit panel — connect each stage to the stored Redis events

Key Redis commands

  • INCR + EXPIRE — per-user guardrail rate limiting
  • FT.SEARCH ... KNN — topic routing against policy vectors
  • HSET / HINCRBY — route seeds and aggregated guardrail stats
  • XADD / XRANGE — auditable guardrail event stream

Why these data structures?

  • String + INCR: Guardrail throttling is just an atomic counter with a TTL window. Simple, fast, and race-free under burst traffic.
  • Vector search: Routing the user message to the right policy/topic bucket benefits from semantic similarity, not just keyword matching.
  • Hash: Route seeds, prompt-injection seeds, and aggregate counters are compact structured records that are easy to update and inspect live.
  • Stream: Every safety decision becomes part of an ordered audit trail you can replay during incident review or demo narration.

Under the hood

  • Redis keys are split by purpose: uc15:rate:{userId} for throttling, uc15:route:* and uc15:injection:* for vector seeds, uc15:stream:audit for the pipeline log, and uc15:stats for counters.

Key Redis commands

  • FT.SEARCH ... KNN — semantic routing and cache similarity lookup
  • HSET / HGETALL — route metadata and aggregated metrics
  • INCR + EXPIRE — gateway rate limiting
  • XADD / XREVRANGE — request log and observability stream

Why these data structures?

  • Vector search: Route selection and semantic cache lookup both rely on similarity, so the same Redis search capability serves two high-value gateway jobs.
  • Hash: Gateway metrics and per-route summaries are naturally small structured objects that need cheap partial updates.

UC17: AI Agent Coordination

What to say

"This use case turns Redis Streams into the coordination backbone for multiple AI specialists. One coordinator decomposes a banking question, pushes one task per specialist into a stream, Consumer Groups fan the work out reliably, and Redis keeps both the live state and the replayable event trail in one place."

Demo steps

  1. Submit a multi-domain banking question — show the coordinator split it into risk, compliance, portfolio, and fraud tasks
  2. Point to the Redis Streams bus — explain how XADD dispatches work and the Consumer Group picks it up in parallel
  3. Watch each specialist card change independently as the coordinator receives progress and tool events
  4. Highlight the RAG context/tool output for one specialist — connect Redis search + domain context to the agent result
  5. Show the final assembled answer and recent event trail — one orchestration flow, many specialized agents

Key Redis commands

  • XGROUP CREATE — create the specialist worker Consumer Group
  • XADD — append coordinator tasks and result events
  • XREADGROUP + XACK — reliable task consumption and acknowledgement
  • HSET / HGETALL — per-agent status and summary state
  • FT.SEARCH ... KNN — RAG lookup for regulation and knowledge context

Why these data structures?

  • Stream + Consumer Groups: This is the durable orchestration bus. Tasks stay in Redis until workers consume and acknowledge them, so the workshop can show fan-out, reliability, and replayable progress with native Redis primitives.
  • Hash: Each agent needs compact mutable state — status, latency, summary, and timestamps. Hash keeps that state cheap to update and easy to inspect live.
  • Vector search for RAG: The specialists are stronger when they retrieve regulation or knowledge-base context instead of answering from a blank prompt. Redis search keeps retrieval and orchestration on the same platform.

Under the hood

  • AgentCoordinatorController streams POST /api/agents/coordinate over SSE while AgentCoordinatorService orchestrates the run.
  • Startup creates consumer groups for uc17:stream:tasks and uc17:stream:results, plus per-agent Hash state at uc17:agent:{agentId} and an event stream at uc17:stream:events.
  • coordinate() fans out one task per specialist, processes them in parallel with CompletableFuture on a fixed thread pool, and uses a Semaphore to prevent overlapping runs.
  • Each worker reads with XREADGROUP, gathers KB and regulation RAG hits, simulates tools, appends results, acknowledges the task, and the coordinator assembles the final response plus live SSE events.

Talking points

  • Streams give you a message bus, audit trail, and replay surface in one Redis data structure
  • Consumer Groups turn one stream into parallel specialist work without losing delivery semantics
  • Multi-agent orchestration is a data problem as much as an LLM problem — Redis handles the coordination state cleanly
  • The same Redis deployment supports orchestration, agent state, and RAG context retrieval
